- Drive-by fix: `src/metrics.py::sharpe_approx` was guarding against
  zero variance with `if std == 0.0`, but numpy's `std` of a constant
  array rounds to ~1e-18 rather than literally 0, so the guard missed
  and returned an astronomical Sharpe-approx (~9e16 for `[0.01]*100`).
  Switched to `std < 1e-12`. Pre-existing bug surfaced by the full
  test-suite run as part of compute_iv verification; would have
  spuriously passed Variant B's E1/E5 success criteria on any
  near-constant return stream.

  `tests/test_storage_split.py` that pin both the mid-month
  partitioning and the pure-month single-file case, and re-routed
  the four contaminated parquets via
  `.phase0/repair_feb_2026_split.py`. Post-repair row arithmetic
  checks: 618+496=1114 (news/sentiment), 9291+8278=17569 (underlying),
  10+10=20 (risk_free). Audit and rationale in

  orchestrator was stopped before the destructive repair and will
  be re-armed once the commit lands.

  sample construction (§4 / §5 of the pre-reg). Six helpers each

  derived from underlying parquet existence so we don't add a

- Built the I/O layer `build_events_frame_for_month` and graduated
  the `match_events` orchestrator stage (gated on backfill_options
  AND score_sentiment). For each in-window event it joins the EWMA
  signal, spot at t / t+30, nearest-Friday expiry, ATM-closest
  strike (frozen for both samples per D1), and 4 NBBO mid-quotes.
  Rows that can't be fully populated are emitted with a
  `failure_reason` (not dropped) so drop rates are auditable;
  `usable_rows` is tracked per chunk in state.json. Mini-smoke on
  20 Jan-2024 events: 20/20 fully populated, all pass the 10%
  spread filter, ATM=472 for spot ~472, expiry 2024-01-05, sensible
  ATM-weekly mids (~2.6 call / ~2.2 put).
- Performance: the first cut ran at ~5.4s/event (4 sequential
  `list_quotes` round-trips). Narrowing the quote window (the
  originally-planned optimization) did NOT help — measured 108s vs
  124s for 20 events, within noise — because the bottleneck is
  round-trip latency (~1.5s/call), not payload size. The fix that
  worked: parallelize the 4 independent quote calls with a
  `ThreadPoolExecutor(4)` (each thread gets its own RESTClient via
  `_client()`, so it's thread-safe). Result: 29s for 20 events,
  ~1.45s/event, ~4x. Full-window projection drops from ~45h to
  ~12h; validation subset ~1.8h. Also kept a correctness fix in
  `fetch_option_mid_quote_at`: query `timestamp_lte=sample` (not
  `sample+window`) so the most-recent-tick-before-sample is the
  first row returned and the `limit` budget isn't burned on
  future-side ticks we discard (a latent false-negative on liquid
  contracts).
